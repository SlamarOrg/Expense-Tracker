# Contributing

Thanks for helping. The most useful contribution is a parser for another bank, so most of this
guide walks through adding one. Bug fixes and translations follow the same rules.

## Ground rules

- **Never commit a real bank statement**, not even a redacted one, and never paste real
  transaction rows into an issue or pull request. Tests run on synthetic statements generated by
  `scripts/make-samples.mjs`. `.gitignore` blocks `*.csv` and `*.pdf` outside `samples/`.
- **No dependencies.** No npm packages, no CDN links. The page must keep working offline from a
  downloaded file. Chart.js and pdf.js are vendored in `vendor/`; see `vendor/VERSIONS.md`.
- **Nothing leaves the browser.** No analytics, no error reporting, no fetches to other hosts.
- English for code, comments and commit messages. User-facing text goes through the dictionaries
  in `src/i18n/` (English and Czech).

If you work on your own statements locally, list your account numbers, name and address in a
file called `.private-denylist` at the repository root, one per line. It is gitignored, and
`tests/no-personal-data.test.mjs` then fails if any of those strings shows up in a file you are
about to commit.

## Setup

Node 22 or newer and an installed Chrome or Edge (for the browser tests). Nothing to install.

```
node --test "tests/*.test.mjs"                  # all tests, browser tests included
node scripts/serve.mjs                          # dev server, open http://localhost:8080/?demo=1
node scripts/make-samples.mjs                   # regenerate samples/ after changing the generator
node scripts/build.mjs                          # dist/dashboard.html, the single-file app
node scripts/build.mjs --with-samples --out dist/demo.html
node scripts/render-check.mjs dist/dashboard.html --lang cs --theme dark
node scripts/parse-cli.mjs <files...> [--rules rules.json]   # parse from the command line
```

Development runs over the dev server because browsers do not load ES modules from `file://`.
The built file has no such restriction. Set `BROWSER` to a Chrome or Edge executable if the tests
cannot find one.

## How the pieces fit

```
statement file ──parser──▶ RawRow[] ──store (IndexedDB)──▶ classify(raw, rules) ──▶ Tx[] ──▶ dashboard
```

- A **parser** (`src/parsers/<bank>.js`) turns file text into `RawRow` objects. It records only
  what the statement says, plus hints that only the parser can know, such as "this card row is a
  refund". It knows nothing about the user's accounts or categories.
- The **store** keeps `RawRow`s, not classified rows. That is why changing accounts or rules in
  the settings re-classifies everything without re-importing.
- The **classifier** (`src/classifier/`) applies the user's rules: transfer, then income, then
  investment, then expense, then a category.

`RawRow` and `Tx` are documented field by field in `src/classifier/types.js`.

## Adding a bank

The steps below use a made-up "Example Bank" with a CSV export. Look at `src/parsers/revolut.js`
for a compact CSV parser and `src/parsers/airbank.js` for a PDF one.

1. **Write a synthetic sample first.** Add an `exampleSample()` function to
   `scripts/make-samples.mjs` that returns the file content in the bank's exact format: encoding,
   delimiter, quoting, header names, date and number formats. Include one row for every case the
   parser must handle: card purchase, refund, foreign currency, fee, transfer to an own account,
   incoming payment, and whatever is special about this bank. Use only fictional people and
   merchants and the fake account range in `samples/README.md`. Write it to
   `samples/example-sample.csv` and run `node scripts/make-samples.mjs`.

2. **Write the parser.** Create `src/parsers/example.js` exporting
   `parseExample(text) -> RawRow[]`. Use `readCsv` from `csv.js` and `isoDate`, `parseCzNumber`
   and `norm` from `src/classifier/normalize.js`. Fill every `RawRow` field. Prefix `id` with the
   bank (`EX|...`) and build it from fields that stay identical when the same transaction appears
   in two overlapping exports, so re-imports are de-duplicated. Use `hints.kind` only where the
   statement itself decides the kind, for example a row type that always means "interest".
   Comment each branch with the statement case it handles.

3. **Register it.** In `src/parsers/index.js` add an entry to `FORMATS`, a filename pattern and a
   content check to `detectFormat()`, and a branch to `parseFile()`. Content sniffing matters:
   users rename files.

4. **Test it.** Create `tests/example.test.mjs` modelled on `tests/revolut.test.mjs`:
   - the committed sample equals the generator output;
   - one test per branch with an explicit assertion on kind, category and amount;
   - a snapshot of all classified rows with `checkSnapshot('example', txs)`.

   The first run writes `tests/snapshots/example.json` and fails on purpose. Read the snapshot,
   then run the tests again. After a deliberate parser change, refresh snapshots with
   `UPDATE_SNAPSHOTS=1 node --test "tests/*.test.mjs"` and review the diff before committing.

5. **Check it in the browser.** Run the dev server, import the sample, and check that the bank
   appears in the filter bar and the import card shows sensible counts. If the bank needs a
   message in the import card, add the key to both `src/i18n/en.json` and `src/i18n/cs.json`;
   `tests/i18n.test.mjs` fails when the two drift apart. Bank names are data and are not
   translated.

6. **Document it.** Add the bank and how to export the statement to the "Supported banks"
   section of `README.md`.

7. **Run everything** before opening the pull request: the full test suite, both builds and a
   render check of each.

### PDF statements

For a PDF-only bank, generate the sample with `scripts/pdf-writer.mjs`. It writes the text cells
in the order you give them, which is the order `src/parsers/pdf-text.js` reads them back. Copy the
real statement's column positions so the line reconstruction is exercised. If the statement
prints totals, compare them with the parsed sums the way `parseAirbankLines()` does and report a
mismatch to the user instead of hiding it.

## Rules and translations

- `rules/default-cz.json` is the starter ruleset. A keyword is a plain substring of the merchant,
  note and message after lowercasing and removing diacritics. A trailing space makes it a whole
  word: `"stk "` matches "STK Brno" but not "částka". Keep keywords to chains and services that
  exist across a whole country, never a single local shop.
- New UI text goes into both dictionaries with the same placeholders. Plural forms use the keys
  `name.one`, `name.few`, `name.many` and `name.other` (Czech needs all four, English only `one`
  and `other`). `tests/i18n-coverage.test.mjs` fails on an untranslated literal in the UI code.

## Commits and pull requests

Small commits with a clear message. One feature or fix per pull request. CI runs the full suite
on Node 22 and 24 and the render checks on the built files.
