# Spec: Bank Statement Dashboard

Status: APPROVED 2026-10-12 (implicitly, by starting planning). Open questions 1, 2 and 4 resolved
the same day; see the end of this file.

## Objective

An open-source, offline spending dashboard that runs entirely in the browser. A user opens one HTML
file, drops their bank statement exports onto it, and gets the same interactive dashboard that the
private Expense Tracker produces today: monthly stacked bars by category, donut, weekly summary,
trend line, searchable transaction table, in-page categorization. No server, no account, no network
request, no install.

Czech banks are supported first (FIO CSV, Air Bank PDF, Revolut CSV) because that is where the
working parsers and format knowledge exist. The project is not branded as Czech-only: the name is
neutral, parsers are pluggable, and the README invites parsers for other banks.

**Users.** People who want to see where their money goes without handing bank credentials to a
budgeting app. They can export a CSV or PDF from internet banking and open a file in a browser.
They may not have Python or Node installed.

**Success looks like.** A stranger clones the repo or opens the GitHub Pages demo, drops their FIO
export on the page, and sees correct monthly totals within a minute, with no data leaving the
browser.

**Source of truth for behaviour.** The private Python implementation in
`Projects/Expense_Tracker/parse_statements.py` and the vault note
`Knowledge/Memory/czech-bank-statement-parsing.md`. The JavaScript port must reproduce its
classification results on the same input. Code is ported, data is never copied.

**Out of scope for v1.** Bank API or open-banking sync, budgets and goals, multi-user, mobile
native apps, UI languages other than English and Czech, Air Bank CSV (deferred until someone
asks), any backend.

## Capability map

| Module id | Responsibility | Depends on |
|---|---|---|
| sample-data | Synthetic FIO, Revolut and Air Bank statements in the real formats, generated by a script | — |
| classifier | Rules engine: normalize text, decide kind (transfer, income, investment, expense, skip) and category | — |
| parsers | One parser per bank producing the normalized row shape. File type detection. Dedup by id | sample-data, classifier |
| dashboard | Existing rendering code, split out of the private HTML and fed from a store instead of an embedded block | classifier |
| import-ui | Drop zone, progress and error reporting, IndexedDB store, settings panel, rules JSON import and export | parsers, classifier, dashboard |
| i18n | English and Czech UI strings, a language switch remembered in the browser | dashboard, import-ui |
| release | Bundler to one HTML file, CI (tests plus headless render check), GitHub Pages demo preloaded with sample data | import-ui, i18n |

Build order: sample-data and classifier in parallel, then parsers, then dashboard, then import-ui,
then i18n, then release. The Air Bank pdf.js feasibility spike runs first of all because it is the
biggest unknown. Module ids are stable and are used in task lists, commit messages and PR titles.
The plan lives in `tasks/plan.md`, the task list in `tasks/todo.md`.

## Tech stack

- Plain JavaScript (ES2022 modules), HTML, CSS. No framework, no TypeScript, no bundler package.
- Chart.js 4.4.4 (already in use), vendored.
- pdf.js (`pdfjs-dist` 4.x legacy build), vendored, for Air Bank PDF text extraction.
- Node 20 or newer for development only: tests, sample generator, static dev server, bundler.
  Zero npm dependencies. `package.json` exists only for scripts and the `"type": "module"` flag.
- Headless Chrome or Edge for the render check (preinstalled on GitHub `ubuntu-latest`).
- Browsers: current Chrome, Edge, Firefox, Safari. The release bundle must work from `file://`.

## Commands

```
node --test tests/                       # unit tests (parsers, classifier, store, bundler)
node scripts/serve.mjs                   # dev server on http://localhost:8080 serving the repo root
node scripts/make-samples.mjs            # regenerate samples/ (deterministic, seeded)
node scripts/build.mjs                   # bundle src/ + vendor/ + rules/ into dist/dashboard.html
node scripts/build.mjs --with-samples    # same, with samples preloaded (the GitHub Pages demo)
node scripts/render-check.mjs dist/dashboard.html   # headless render: data-ready="1", #errlog empty
```

`render-check.mjs` finds the browser via `$BROWSER`, then the default Edge and Chrome paths on
Windows, macOS and Linux.

## Code style

Match the existing dashboard: small pure functions, no classes except `Rules`, single quotes,
semicolons, two-space indent, `const` by default. Each parser is a pure function of text, so tests
never need a browser. Data shapes are documented with JSDoc typedefs, not TypeScript.

```js
/**
 * @typedef {object} Tx
 * @property {string} d    ISO date of the purchase (card) or execution (transfer)
 * @property {number} amt  CZK spend: positive = money out, negative = refund
 * @property {number} orig signed amount as printed on the statement
 * @property {string} cur  original currency code
 * @property {string} m    merchant or payee, max 80 chars
 * @property {string} n    note, max 120 chars
 * @property {string} s    source bank: 'FIO' | 'Airbank' | 'Revolut'
 * @property {string} t    statement row type as printed
 * @property {'expense'|'investment'|'transfer'|'income'|'skip'} k  kind, decided before category
 * @property {string} c    category (after overrides)
 * @property {string} c0   category from rules, before overrides
 * @property {string} cp   counterparty account 'number/bank' or ''
 * @property {string} id   stable id for dedup, prefixed by bank
 */

export function parseRevolut(csvText, rules) {
  const rows = readCsv(csvText, { delimiter: ',' });
  const out = [];
  for (const row of rows) {
    const state = pick(row, 'State', 'Stav').toUpperCase();
    if (!COMPLETED.has(state)) continue;
    // ...one decision per branch, same order as the Python reference
  }
  return out;
}
```

Conventions: files and ids in kebab-case, functions in camelCase, constants in UPPER_SNAKE.
English only, including comments. Czech strings appear only as statement vocabulary in parsers
and rules. Every parser branch that exists in the Python reference keeps a comment naming the
statement case it handles (for example "Kredit: prefix means card refund").

## Module specs

### sample-data

Deterministic generator producing three files that look like real exports and exercise every
parser branch.

- FIO: UTF-8 with BOM, `;` delimited, all fields quoted, Czech headers, comma decimals. Must include
  card purchases with `dne` and `částka` in EUR, a `Kredit:` refund, an ATM withdrawal, a Revolut
  top-up card row, a transfer to an own account, a payment to a fixed counterparty account with
  empty message and note, interest and interest tax rows, an incoming salary.
- Revolut: `,` delimited, Czech headers. Must include `Platba kartou` with a fee, `Směna` leg
  pairs, `Dobíjení`, `TRADE` buy and sell, `Převod` to a broker, `Poplatek`, one row not
  `DOKONČENO`.
- Air Bank: a real PDF written by `scripts/pdf-writer.mjs` (dependency-free, text only). Header
  with `Číslo účtu`, `Odepsáno z účtu`, `Připsáno na účet`. Blocks in the modern layout and in the
  older layout (account on the transaction-code line), a two-line type, a block with text after the
  amount line, a card refund (`Vrácení`), a reward (`Odměna`), page furniture and the
  `Vklad na tomto účtu podléhá` footer. Czech diacritics via a `/Differences` encoding; if pdf.js
  cannot extract them from base-14 fonts, the fixture falls back to ASCII and the diacritics path
  is covered by the private manual check against Martin's real statements.
- Fake people and merchants only. No real account numbers: own and counterparty accounts come from
  a reserved fake range, documented in `samples/README.md`.
- Acceptance: `make-samples.mjs` is idempotent (same bytes on re-run); every parser branch listed
  above is hit by at least one row, proven by a coverage assertion in tests.

### classifier

Port of `norm`, `parse_cz_number`, `iso`, `Rules`, `tx` and `classify_flow`.

- Rules JSON keeps the private `categories.json` schema exactly (`fx_rates_to_czk`, `own_accounts`,
  `transfer_keywords`, `investment_accounts`, `investment_keywords`, `categories`,
  `folded_in_charts`, `category_accounts`, keys starting with `_` ignored), so a user of the private
  tool can import their own rules unchanged.
- `rules/default-cz.json` ships generic Czech keywords and empty account lists.
- Kind precedence is fixed: transfer, then income, then investment, then expense.
- Acceptance: a table-driven test with at least 30 (text, counterparty, amount, expected kind,
  expected category) cases, including the `stk ` / `částka ` false-positive regression.

### parsers

- `detectFormat(file)` by file name first (same patterns as the Python `find_files`), then by
  content sniffing (FIO header `Datum;`, Revolut header `Typ,Produkt`, PDF magic bytes), so a
  renamed file still imports.
- Parsers return `RawRow` objects, not `Tx`: bank, dates, signed amount, currency, merchant, note,
  statement type, counterparty, matching text, and bank-specific hints the parser alone can know
  (card refund, interest, Revolut top-up, fee amount, forced kind). `classify(raw, rules)` in the
  classifier turns a `RawRow` into a `Tx`. The store persists `RawRow`, so changing rules or own
  accounts re-classifies everything without re-importing files.
- `parseFio`, `parseRevolut`: straight ports, including the FIO card regex, refund netting, fee
  handling, Revolut-as-transfer rules and the `REVOLT` bank code rule.
- `parseAirbank`: `pdfToLines()` turns pdf.js `getTextContent()` items into lines in content-stream
  order, starting a new line on a y change or a large x gap, and the block parser is the Python
  port. The printed `Odepsáno z účtu` total is compared with the parsed debit sum and reported per
  file. A mismatch is shown to the user, never hidden.
- pdf.js runs on the main thread with a fake worker so the bundle works from `file://`. If 4.x
  refuses without `workerSrc`, the worker source is inlined and started from a Blob URL. This is
  decided in the first parsers task and recorded here.
- Dedup by `id` across all imported files, including re-importing the same file.
- Acceptance: each sample file parses with zero problems; the Air Bank sample's debit total matches
  to the cent; a snapshot test pins every row of every sample, so a parser change shows up as a
  diff. Private check, not in CI: Martin runs the JS parsers on his real statements and the row
  count and category totals equal the Python output.

### dashboard

- The existing IIFE is split into modules without changing behaviour: state, renderAll, upsert,
  charts, tables, tooltip, theme, overrides.
- Data comes from the store, not from `window.EXPENSE_DATA`. Footer shows imported files and dates
  instead of "Data generated".
- The `c0` field and `applyOverrides()` stay; "Save overrides.json" becomes "Export overrides"
  and is joined by "Import overrides".
- Empty state: when the store is empty the page shows the drop zone and a link to the samples
  instead of empty charts.
- Acceptance: with the sample data loaded, every existing feature in the private README works;
  headless render check passes in light and dark; no console errors.

### import-ui

- Drop zone and file picker accept multiple files. Each file shows bank, row count, kinds
  breakdown, dedup count, problems and the Air Bank total check.
- IndexedDB store with versioned schema. "Forget my data" wipes everything and is confirmed.
- Settings panel: own accounts, investment accounts, FX rates, rules JSON import and export, reset
  to defaults. Changing settings re-classifies all stored rows from their raw fields, so the store
  must keep what a parser needs to re-run classification (the raw text and counterparty).
- Privacy statement in the UI: files are read in the browser, nothing is uploaded, data lives in
  this browser's storage only.
- Acceptance: importing the three samples in any order yields the same store; re-importing adds
  zero rows; settings changes re-categorize without re-import; works in Chrome, Edge, Firefox from
  `file://` via the bundle.

### i18n

- Every user-visible string in the UI goes through `t(key, params)`. English is the fallback for a
  missing Czech key; a missing key in both throws in tests and renders the key in the browser.
- `en.json` and `cs.json` have identical key sets, enforced by a test.
- The language switch sits next to the theme switch, defaults to the browser language when it is
  Czech and to English otherwise, and is remembered in `localStorage`.
- Category names, bank names and the statement vocabulary are data, not UI strings, and are not
  translated.
- Acceptance: switching language re-renders every panel, chart label and tooltip without reload;
  the key-parity test passes; the render check passes in both languages.

### release

- `build.mjs` inlines `styles.css`, `vendor/`, `rules/default-cz.json` and the modules into one
  `dist/dashboard.html` (module graph flattened by the script, no third-party bundler). Target
  size under 3 MB. `--with-samples` embeds the sample rows for the demo.
- `ci.yml`: Node 20, `node --test`, build, render check. Fails on any `#errlog` content.
- `pages.yml`: deploys the demo build on push to `main`. The demo banner says the data is fake.
- README: what it is, a screenshot, the privacy promise, supported banks and how to export from
  each, how to run, how to add a bank parser (link to CONTRIBUTING.md), credits.
- Acceptance: a fresh clone passes CI; the Pages URL renders the demo; the downloaded bundle opens
  from `file://` in Chrome and Firefox and imports the samples.

## Testing strategy

- Unit tests with Node's built-in runner, `tests/*.test.mjs`, one file per module. Fixtures are the
  generated samples, never hand-edited.
- Snapshot tests for parser output (JSON files under `tests/snapshots/`, updated deliberately with
  `UPDATE_SNAPSHOTS=1`).
- Table-driven tests for the classifier.
- Browser-level check: `render-check.mjs` in headless Chrome or Edge, asserting `data-ready="1"`
  and an empty `#errlog`, run in CI against the demo build.
- Personal-data guard: `tests/no-personal-data.test.mjs` reads an optional, gitignored
  `.private-denylist` (one string per line: Martin's account numbers, names, addresses) and fails if
  any appears anywhere in the repo. The denylist itself never enters git. The test is skipped
  when the file is absent, so it passes in CI and bites locally.
- Coverage target: every parser branch covered by a sample row, checked by the coverage assertion
  in the parser tests. No percentage threshold.

## Boundaries

**Always**
- Port code from `Expense_Tracker`; never copy statements, `overrides.json`, the embedded data
  block, or account numbers from `categories.json`.
- Run `node --test` and the render check before every commit.
- Keep parsers pure (text in, rows out) so they are testable in Node.
- Keep the row shape and the rules JSON schema compatible with the private tool.
- Report parser problems and total mismatches to the user in the UI.

**Ask first**
- Adding any npm dependency or any CDN reference.
- Changing the `Tx` shape, the rules JSON schema, or the IndexedDB schema after the first release.
- Changing GitHub workflows, repo settings, or the licence.
- Anything that sends data anywhere, including error reporting or analytics.

**Never**
- Commit real financial data, `dist/` output, or the `.private-denylist`.
- `git init` inside `Expense_Tracker`, or sync files between the two folders automatically.
- Push to GitHub, create the remote, or publish a release. Martin does that.
- Make a network request at runtime.

## Success criteria

1. One file, `dist/dashboard.html`, opened from `file://` with no network access, imports all three
   sample files and renders every chart and table.
2. For Martin's real statements, the JS parsers produce the same row count, kinds and per-category
   totals as `parse_statements.py` (private manual check, documented in the task list).
3. The Air Bank parser's debit total matches the printed total for the sample and for both real
   PDFs.
4. `node --test` passes with zero npm dependencies; CI is green on a fresh clone.
5. The GitHub Pages demo renders with fake data and states that it is fake.
6. The personal-data guard finds nothing in the repo with Martin's denylist present.
7. A reader of README.md can add a parser for a new bank by following CONTRIBUTING.md without
   asking questions.

## Decisions taken on open questions (2026-10-12)

1. **Naming and language.** Repo `bank-statement-dashboard`, neutral positioning, plus a Czech and
   English UI language toggle (the `i18n` module).
2. **Default rules.** `default-cz.json` is a cleaned subset of Martin's keywords: national chains
   and services stay, local businesses and anything hinting at a location are dropped. The dropped
   list is shown to Martin for review before the file is committed.
3. **Migration.** Martin will switch to the public tool once it matches the Python output. The last
   task imports his real statements and rules into a local build and compares totals.

## Open questions

1. **GitHub remote.** Which account and visibility at creation, private first then public, or
   public from the first push?
2. **pdf.js on `file://`.** Decided by the spike (T2, 2026-10-12): the worker source is inlined
   in the page as a `text/plain` script, turned into a Blob URL and used as `workerSrc`. Works in
   headless Chrome and Edge from `file://`. pdf.js line reconstruction (new line on `hasEOL` or a
   y change) reproduced `pdftotext -raw` line for line on both real Air Bank statements and on
   the synthetic PDF with diacritics. Firefox could not be tested (not installed). pdf.js
   detaches the input buffer, so parsers must pass a copy.
3. **Folder location.** `Projects/` is inside OneDrive. A `.git` directory under OneDrive sync is a
   known source of corrupted repos and lock errors. Keep it here, or move the repo to a folder
   outside OneDrive before `git init`?
